## 1. Current Architecture

SAT Studio V6 is a single self-contained `index.html` file (no build step, no server, no
`package.json`). All application logic — UI, state, data, and network calls — lives in one
inline `<script>` block. There is currently **no AI/LLM integration of any kind**. What might look
like "AI features" (vocabulary, idioms, grammar, SAT quiz, summary, ESL dialogue) are all
generated by local static data and deterministic/heuristic JavaScript logic. The **only** feature
that talks to an external network service is sentence-level translation, and the services it talks
to (MyMemory, Lingva) are keyless machine-translation APIs, not AI providers.

### 1.1 Current flow map (actual function names)

```
User pastes passage → analyze()
  ├─ splitSentences(text)                    → sentence array
  ├─ words(text)                             → unique lowercase word list
  ├─ vocab build (inline in analyze())
  │    ├─ dictionary[w] lookup               → known-word entries
  │    ├─ fallbackKoreanGloss(w)              → heuristic gloss for unknown words
  │    └─ levelFor(w)                        → grade-level heuristic (9–12)
  ├─ phraseBank filter/supplement (inline)    → idiom/phrase list
  ├─ makeQuestions(text, sents, vocab, n)     → SAT quiz items (fully templated, local)
  │    ├─ englishOnly(s, fallback)            → guards non-English leakage into quiz text
  │    └─ shuffleChoices(q)                   → randomizes correct-answer position
  ├─ state.analysis = {...}                   → assigned BEFORE translations resolve
  ├─ render() → overview(a)                   → Summary tab (pure local aggregation)
  └─ runWithConcurrency(sents, CONCURRENCY_LIMIT, worker)
       └─ worker: translateSentenceReliable(s)
            ├─ translationCache.get/set(s)    → session-level Map cache
            ├─ tryMyMemory()                  → fetch() api.mymemory.translated.net
            │    (2 attempts, RETRY_BACKOFF_MS apart)
            ├─ translateLingva(s)             → fetch() each LINGVA_INSTANCES host in order
            ├─ simpleTranslate(s)             → local phrase-map fallback (no network)
            └─ returns {ko, status:'success'|'error', source}
       → updateTranslationRow(i)              → patches one DOM row via translationRowTemplate
       → retrySentence(i)                     → user-triggered per-row retry (bypasses cache)

render() dispatch (tab switch or after analyze()):
  overview(a) | translation(a) | vocab(a) | phrases(a) | grammar(a) | examples(a) | esl(a) | sat(a)

Local persistence:
  saveCurrent() → getSavedList() → localStorage["satStudioSaved"]
  loadSaved(id) / deleteSaved(id) / renderSaved()
```

### 1.2 Function-to-capability map

| Capability | Primary function(s) | Data source | Network? |
|---|---|---|---|
| Translation | `translateSentenceReliable()`, `tryMyMemory()` (nested), `translateLingva()`, `simpleTranslate()` | MyMemory API → Lingva API → local phrase map | Yes (MyMemory, Lingva) |
| Vocabulary generation | inline in `analyze()`, `fallbackKoreanGloss()`, `levelFor()` | local `dictionary` object + heuristics | No |
| Idiom/phrase generation | inline in `analyze()` (phraseBank filter), `phrases()` | local `phraseBank` array | No |
| Grammar analysis | `grammarInsights()`, `simpleGrammarHighlight()`, `grammar()` | regex heuristics + 2 hardcoded sample-passage special cases | No |
| SAT quiz generation | `makeQuestions()`, `englishOnly()`, `shuffleChoices()`, `sat()`, `gradeQuiz()` | fixed local question templates | No |
| Summary | `overview()` | aggregation of already-computed `state.analysis` fields | No |
| ESL dialogue | `esl()` | fixed local dialogue template with vocab substitution | No |
| Pronunciation scoring | `evaluatePronunciation()`, `startAudioMetrics()`, etc. | browser `MediaRecorder`/`AudioContext`/`SpeechRecognition` APIs | No (browser-local) |
| Caching | `translationCache` (Map) | in-memory, session-scoped | — |
| Local storage | `getSavedList()`, `saveCurrent()`, `loadSaved()`, `deleteSaved()` | `localStorage["satStudioSaved"]` | No |
| UI loading/error states | `translationRowTemplate()` (loading/error/success branches), `.sentence.loading`/`.sentence.error` CSS | — | — |

### 1.3 Network requests present in the code today

Exactly two `fetch()` call sites exist in the entire file:

1. `tryMyMemory()` (nested inside `translateSentenceReliable()`) — `https://api.mymemory.translated.net/get?...`
2. `translateLingva()` — `https://<host>/api/v1/en/ko/...` for each host in `LINGVA_INSTANCES`

`dictionaryLinks()` emits `<a target="_blank">` links to Merriam-Webster/Oxford/Cambridge/Thesaurus —
these are user-navigated outbound links, not programmatic requests, and are out of scope for the
router.

## 2. Target Architecture

Introduce a single, provider-agnostic **AI Router** layer that sits between application logic
(`analyze()`, tab render functions) and any provider — local/offline logic, today's MyMemory/Lingva
chain, or future LLM providers (Gemini, Nemotron, Gemma, Phi, OpenAI, Claude, and providers not yet
known). The router does not itself implement translation, vocabulary, or any other capability; it
selects and calls a **provider adapter** according to a **routing policy** per **task type**, and
returns a **normalized response**.

```
User Input
  → analyze() / tab render functions            (unchanged orchestration)
    → aiRouter.request(taskType, payload, options)
        → routing policy for taskType
            → provider adapter 1 (e.g. offline/legacy)
            → provider adapter 2 (e.g. mymemory+lingva chain, wrapped)
            → provider adapter 3+ (future: gemini / nemotron / gemma / phi / openai / claude)
        → normalized RouterResponse
    → existing render/update functions consume normalized data
        (translationRowTemplate, vocab(), phrases(), grammar(), sat(), overview())
```

Critically, in Phase 1/2 the router's job for `translation` is to **wrap the existing pipeline**,
not replace it — see §7 (Translation Compatibility Plan). For task types that currently have no
AI behavior at all (vocabulary-for-unknown-words, idioms-beyond-the-bank, grammar-beyond-heuristics,
quiz, summary, explanation), the router gives the codebase a place to *later* add real AI providers
without another architectural change, while defaulting to today's local/offline logic as the first
routing step so the app keeps working identically with zero providers configured.

## 3. AI Router Interface

```js
// Illustrative stub only — not wired into analyze() or any render function in this phase.
const aiRouter = {
  async request(taskType, payload, options = {}) {
    // 1. look up routing policy for taskType
    // 2. try providers in policy order, bounded attempts, no infinite retry
    // 3. return a normalized RouterResponse (never throws for expected failure paths)
  }
};
```

**Call shape:** `aiRouter.request(taskType, payload, options)`

- `taskType` — string, one of the task types in §5.
- `payload` — task-specific input (e.g. `{ text: "..." }` for translation, `{ word: "..." }` for
  vocabulary).
- `options` — optional: `{ timeoutMs, bypassCache, preferredProvider, maxAttempts, signal }`.
  Defaults must reproduce today's constants (`REQUEST_TIMEOUT_MS`, `RETRY_BACKOFF_MS`,
  `CONCURRENCY_LIMIT`) rather than inventing new values.

**Normalized response:**

```js
{
  success: true,        // boolean — true only if data is usable
  provider: "offline",  // adapter id that produced the result
  model: null,          // provider/model identifier, null for non-LLM adapters
  data: { ... },         // task-specific payload, shape fixed per taskType (see §5)
  latencyMs: 812,
  fallbackUsed: false,   // true if a non-primary provider in the chain answered
  error: null            // populated only when success:false
}
```

This shape is a superset of what `translateSentenceReliable()` already returns
(`{ko, status, source}`); the router's `translation` adapter must still expose the exact
`{ko, status, source}` shape inside `data` (or the router must translate its normalized shape back
into that exact shape at the call site) so `translationRowTemplate()`, `updateTranslationRow()`,
`retrySentence()`, and `saveCurrent()`'s SAVE-1 guard need no changes.

## 4. Provider Adapter Contract

```js
// Illustrative stub only.
const providerAdapter = {
  id: "offline",                                   // stable string identifier
  offline: true,                                    // true = no network call
  costTier: "free",                                 // "free" | "paid" | "unknown"
  canHandle(taskType) { /* boolean */ },
  async request(taskType, payload, options) {
    // returns { success, data, model, error } — router adds provider/latencyMs/fallbackUsed
  },
  async healthCheck() { /* boolean, cheap/cached — optional for offline adapters */ }
};
```

Minimum contract each adapter must implement: `id`, `canHandle(taskType)`, and
`request(taskType, payload, options)`. `healthCheck()` is optional but recommended for any
network-backed adapter (mymemory, lingva, and every future LLM adapter) so the routing policy can
skip a known-down provider without spending a full request timeout. `offline` and `costTier` are
metadata the routing policy reads to implement §6's "offline first, free before paid" rule — they
are not behavioral requirements on the adapter itself.

Future adapters (not implemented in this phase): `offline` (wraps existing local logic),
`mymemory-lingva` (wraps the existing translation chain unchanged), `gemini`, `nemotron`, `gemma`,
`phi`, `openai`, `claude`, and any provider not yet known — the contract has no
provider-specific assumptions, so a new provider only needs to implement these three methods.

## 5. Task Types

Derived from the actual tabs/functions in `index.html`, not invented abstractly:

| Task type | Maps to existing function(s) | Current implementation | Notes |
|---|---|---|---|
| `translation` | `translateSentenceReliable()` | MyMemory → Lingva → phrase map → error | Only task type with a real existing reliability pipeline; must be preserved exactly (§7) |
| `summary` | `overview()` | local aggregation, no generation | Future: abstractive AI summary as an *additional* option, not a replacement |
| `vocabulary` | vocab-build block in `analyze()`, `fallbackKoreanGloss()` | dictionary lookup, then length/suffix heuristics | AI providers would supplement words missing from local `dictionary`, same fallback position `fallbackKoreanGloss()` occupies today |
| `idioms` | phraseBank filter in `analyze()`, `phrases()` | fixed local phrase list, filtered by substring match | AI providers could detect idioms/phrasal verbs not in `phraseBank`, same supplemental role |
| `grammar` | `grammarInsights()` | regex heuristics + 2 hardcoded sentence special-cases | AI providers would replace/extend the generic regex branch only; the 2 hardcoded cases are out of scope for this router entirely |
| `quiz` | `makeQuestions()` | fixed local templates | AI providers would generate passage-specific questions as an alternative to the fixed templates |
| `explanation` | *(none today)* | — | New, general-purpose task type reserved for future free-form tutoring/clarification requests; no existing function to preserve |

`explanation` is included per the objective's task-type guidance even though no current UI surface
uses it, so the router's taxonomy doesn't have to be redesigned again the first time a "explain
this to me" feature is proposed.

## 6. Routing Policy

General template applied per task type, first-generation:

```
1. Cache (task-appropriate; translation already has one — translationCache)
2. Offline / local adapter (today's existing function, wrapped verbatim)
3. Existing free/keyless network chain, translation only (MyMemory → Lingva, unchanged order)
4. Configured AI providers, in user/operator-defined priority order — NOT ACTIVE in Phase 1/2
5. Explicit failure state (never a placeholder string presented as real content)
```

Per-task instantiation:

- **translation:** `cache → legacy chain (mymemory → lingva → simpleTranslate) → [future AI providers, opt-in only] → error`. This is the existing order, unchanged. AI providers are appended, not inserted ahead of, the proven chain, so default behavior cannot regress.
- **vocabulary:** `dictionary lookup → heuristic fallback (fallbackKoreanGloss/levelFor) → [future AI providers for words the heuristics still can't confidently classify] → existing heuristic result stands (never a hard error — vocabulary must never be empty)`.
- **idioms:** `phraseBank exact match → phraseBank supplemental fill → [future AI idiom detection, additive only] → existing supplemental result stands`.
- **grammar:** `hardcoded sample-passage cases (unchanged, out of router scope) → regex heuristics → [future AI grammar explanation, replacing only the generic regex branch's output] → existing heuristic note stands`.
- **quiz:** `fixed local templates (unchanged default) → [future AI-generated passage-specific questions, opt-in] → fixed templates stand as guaranteed fallback`.
- **summary:** `local aggregation (unchanged default) → [future AI abstractive summary, additive] → local aggregation stands`.
- **explanation:** `[future AI providers only] → explicit "unavailable" state` — there is no local fallback for a task type with no existing implementation.

Cross-cutting rules (apply to every task type): no more than one retry per network-backed adapter
before moving to the next adapter in the chain (matches `RETRY_BACKOFF_MS`'s existing single-retry
pattern); total attempts across the whole chain must be bounded and finite (no adapter is retried
after the chain has moved past it); a "free before paid" ordering only applies once real AI
providers exist — it does not change today's ordering, since MyMemory/Lingva are already free and
already first.

## 7. Translation Compatibility Plan

Milestone 2 translation reliability is protected behavior. The router must preserve, unchanged:

- **Batching/concurrency** — `runWithConcurrency()` + `CONCURRENCY_LIMIT=3` stays at the
  `analyze()` dispatch layer. The router is called *inside* the existing per-sentence worker
  callback; it does not replace or wrap the concurrency loop itself.
- **Cache** — `translationCache` (Map) keeps being read/written exactly as today. Recommended:
  the wrapped legacy adapter continues to own this Map directly in Phase 2, rather than the router
  introducing a second, parallel cache layer that could drift out of sync.
- **Retry** — the existing MyMemory 2-attempt/`RETRY_BACKOFF_MS`-backoff behavior, and Lingva's
  ordered-mirror-list attempt, are preserved inside the wrapped adapter untouched.
- **Lingva fallback** — `translateLingva()` and `LINGVA_INSTANCES` stay exactly as implemented.
- **Per-row loading/error states** — `translationRowTemplate()`'s `loading`/`error`/`success`
  branches, and the `.sentence.loading`/`.sentence.error` CSS, are UI-layer and untouched by the
  router's introduction.
- **Retry UI** — `retrySentence(i)` keeps calling into the same translation logic (now via the
  router, wrapped) with `bypassCache:true`, preserving its current behavior.
- **SAVE-1 behavior** — `saveCurrent()`'s block on any `status:'loading'` entry is state-layer
  logic that does not depend on *how* a translation was produced, only on its `status` field, which
  the router-wrapped adapter must continue to populate identically.

**Mechanism:** wrap `translateSentenceReliable()` as the `request()` implementation of a
`legacy-translation` provider adapter (§4), registered as the sole/first entry in the `translation`
routing policy (§6). `aiRouter.request('translation', {text: s}, options)` becomes a thin pass
through the router that calls this adapter and returns `{ko, status, source}` inside `data`,
identical to what `translateSentenceReliable(s)` returns today. This makes the router's
introduction a structural no-op for translation until a second (AI) provider is actually
registered and enabled — the exact requirement in the phase's constraints ("existing translation
reliability behavior must not regress").

## 8. File Structure Decision

| Criterion | A. Keep inline in `index.html` | B. Extract to separate JS modules |
|---|---|---|
| Regression risk | Low–Medium — same file already proven to accept scaffolding (Milestone 2 did this) | Medium–High — `<script type="module">` fails silently under `file://`, which is how this app is likely opened by non-technical users; a real regression to the "just double-click index.html" workflow |
| Maintainability | Degrades slowly as file grows (currently 932 lines) | Improves as complexity grows; adapters testable in isolation |
| Offline portability | Best — one file, no path/module resolution concerns | Worse without a bundler — multiple files must travel together |
| Git diff clarity | Diffs land in one file; mitigated by the same block-comment convention Milestone 2 already established | Better — new files show as clean additions |
| Future provider expansion | Fine — same additive pattern used for Lingva | Better long-term — one file per adapter |
| Browser compatibility | Best — plain `<script>`, no bundler/transpiler | Requires ES modules or a build step |
| Ease of distribution | Best — matches the app's existing single-file distribution model exactly | Worse — needs either a server or a new build step, neither of which this project has today |

**Recommendation for Phase 2: Option A — keep the router and adapters inline in `index.html`**,
organized as a clearly delimited, heavily commented section following the exact convention already
established for Milestone 2's scaffolding (block comments citing this architecture doc by section
number, the same way existing code cites `02-ARCHITECTURE.md`). This preserves the single-file
distribution property, avoids introducing a build step or module-loading regression risk, and
matches precedent that has already shipped successfully in this codebase. Revisit Option B only
if/when the router and its adapters grow large enough (e.g., several real AI providers integrated)
that file size and diff noise become the dominant risk — at that point, introducing a build step
should be its own explicitly scoped, CEO-approved milestone, not something adopted silently.

## 9. Security Model

- **API keys must not be embedded in distributable HTML.** This file is, by design, a static
  document anyone can view-source. Any real secret key placed directly in `index.html`'s JS is
  fully exposed the moment the file is shared, hosted, or opened. This is a hard constraint on any
  provider requiring a secret key (OpenAI, Claude, Gemini, and most commercial LLM APIs).
- **Browser-to-provider direct calls.** Today's MyMemory/Lingva calls are safe as direct
  browser→API calls because they are keyless, free, and CORS-friendly by design. Most commercial
  LLM APIs either require a secret key incompatible with direct browser exposure or block direct
  browser calls via CORS specifically to prevent this.
- **Need for backend/proxy in commercial deployment.** Any provider requiring a real secret key
  needs a thin backend/proxy that holds the key server-side and forwards requests on the app's
  behalf; the browser must never hold that key. This is a hard requirement before any paid-tier
  OpenAI/Claude/Gemini/etc. adapter can be enabled outside of the developer's own local testing.
- **Development-only keys.** Local testing may use a developer-entered key stored only in that
  developer's own browser/local environment, clearly labeled as never to be shipped, and never
  committed to git or baked into the distributed `index.html`.
- **Student privacy.** Passages and any future AI-generated tutoring content may contain
  student-authored text. Sending this to a third-party AI provider means student work leaves the
  browser/device. Given this app's Korean-language SAT-prep audience likely includes minors, any
  provider beyond the already-existing keyless MyMemory/Lingva translation calls needs explicit
  user-facing disclosure (which provider, what data, opt-in) before being enabled, and the
  `offline` adapter should remain a first-class, always-available option for privacy-sensitive
  deployments.
- **Logging of prompts/responses.** No request/response logging exists today. Any future logging
  (for QA or router tuning) must avoid persisting raw student passage text or other PII without
  explicit disclosure and a defined retention limit, and should default to off.

No secret, key, or backend is created by this document or this phase.

## 10. Regression Risks

**HIGH**
1. Changing `translateSentenceReliable()`'s call order or its `{ko, status, source}` return shape
   — breaks `translationRowTemplate()`, `updateTranslationRow()`, `retrySentence()`, and
   `saveCurrent()`'s SAVE-1 guard directly. *Mitigation:* wrap, never rewrite, this function; verify
   its output shape is unchanged before/after wrapping.
2. Introducing `<script type="module">` or any external script dependency that fails silently
   under `file://` usage. *Mitigation:* Option A (§8) — stay inline, no module loading.
3. Restructuring `analyze()`'s dispatch loop (`runWithConcurrency`/`CONCURRENCY_LIMIT`) while
   wiring in the router — risk of reintroducing the pre-Milestone-2 blocking-render bug.
   *Mitigation:* the router call replaces only the inner `translateSentenceReliable(s)` call inside
   the existing worker callback; the loop itself is untouched.

**MEDIUM**
4. Cache drift if the router adds a second cache layer instead of reusing `translationCache`.
   *Mitigation:* Phase 2 explicitly keeps the legacy adapter owning `translationCache` directly.
5. Shape drift in wrapped vocabulary/idiom/grammar/quiz data (e.g. vocab's 7-element data array,
   phrase tuples) that downstream render functions index into positionally. *Mitigation:* any
   wrapping preserves exact existing data shapes, verified with this project's established
   throwaway-jsdom testing convention (per `TESTING_STANDARDS.md`).
6. Divergent timeout/backoff/concurrency constants if router/adapter code redefines
   `REQUEST_TIMEOUT_MS`, `RETRY_BACKOFF_MS`, or `CONCURRENCY_LIMIT` instead of reusing them.
   *Mitigation:* reuse the existing constants; do not introduce parallel values.

**LOW**
7. Future AI provider adapters (Gemini/Nemotron/Gemma/Phi/OpenAI/Claude) being added but
   unconfigured — low risk while they remain entirely absent, as required by this phase's
   constraints. Risk only materializes when a given adapter is actually enabled in a later phase.
8. This documentation-only commit being bundled with unrelated changes. *Mitigation:* verified via
   checksum and `git diff --stat` immediately before commit (see Final Verification below).
